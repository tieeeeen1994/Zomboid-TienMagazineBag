# Tien's Ammo Bags

Project Zomboid mod. The live code is under `Contents/mods/TienMagazineBag/42/` (B42). The top-level `Contents/mods/TienMagazineBag/media/` is the outdated B41 version.

The Lua source has no comments on purpose. The reasoning behind non-obvious code lives here. Update this file when that reasoning changes.

## MagazineBag_Core.lua

### Bag assignment (multiplayer)
- `AssignMagazineBag` sets `modData.isMagazineBag` locally and sends the `assignBag` client command. In B42 MP the inventory is server-authoritative, so the server's copy of the item has to get the flag too or the assignment is lost on logout. `MagazineBag_Server.lua` handles that command, then calls `syncItemModData` to push the server's copy back to the owner. That is the direction vanilla uses it in (from `complete()`, e.g. `ISChangeFishingRodEquip`). The client doesn't call it: it does nothing useful there, and could pull back the server's copy from before the change.

### Gunworks support
Everything Gunworks-specific keys off the framework (`SWMG`), not a particular gun pack, so any pack built on it is covered (Guns of Marz, VWP2GoM, ...). It has no setting: it's always on when `SWMG` is active. `GetGunworks(name)` only requires `WeaponSystems/Utils/<name>` when `SWMG` is active, and resolves it lazily so file load order doesn't matter. Without it, every path falls back to vanilla and behaves as it always did. Ammo Maker only handles crafting and casings, so it plays no part here.

### Assigned ammo
Gunworks puts each magazine in an ammo family (e.g. `"5.56x45mm"`) that lists several round types: ball, HP, AP, subsonic. A magazine loads one type at a time, whatever `getAmmoType()` currently says.
- `GetAmmoFamily` falls back to the family of the item's current round (`Ammo.FindBulletEntry`) when the item itself isn't registered. Packs register magazines but often not the guns: Guns of Marz lists the STANAGs under `5.56x45mm`, but not the M16s. And Gunworks swaps a gun's `getAmmoType()` to whatever round it's firing, so without the fallback, Store would bag only that one round type.
- The assignment is `modData.MagazineBag_AmmoType`, synced like `isMagazineBag`. `GetAssignedAmmo` ignores a value that isn't in the item's family, so a stale one (Gunworks removed, family changed) is harmless.
- `GetReloadRoundTypes`: an assigned magazine takes only its assigned round and waits if there is none. That is the point of assigning it. An unassigned one takes whatever is on hand, in the player's Gunworks reload order (`GunworksAmmoPref`), and can mix types to fill up. Gunworks' `AmmoList` hooks track each round, so mixing is safe.
- Guns that load loose rounds (`LoadsLooseRounds`: revolvers, shotguns, lever-actions, anything whose feed kind isn't "magazine") can be assigned a round themselves. On a magazine-fed gun the same modData key only holds the inserted magazine's assignment while it's in there (see `MagazineBag_AmmoCarry.lua`), so assigning those guns directly isn't offered.
- `GetReloadRoundTypes`: an unassigned speedloader or magazine takes the assignment of the loose-round gun in hand when they share a family. So a revolver assigned to subsonic gets its speedloaders filled with subsonic, which it will then accept.
- `GetFetchableRoundTypes` narrows to the gun's own assignment. Storing still bags the whole family.
- Inserting a magazine destroys the item, and ejecting creates a new one with `instanceItem()`, so modData would be lost. `MagazineBag_AmmoCarry.lua` moves the assignment onto the gun in `ISInsertMagazine:loadAmmo` and back onto the new magazine in `ISEjectMagazine:unloadAmmo`. Those run in SP or on the MP server, so the owning client is told through the `syncAmmo` server command. The ejected magazine is found by diffing item IDs, not by type: Gunworks swaps the gun's magazine type around inside the same call. Both hooks skip loose-round guns, because inserting a speedloader into a revolver also goes through `loadAmmo`, and copying would overwrite the revolver's own assignment.
- **Load order.** The 42 `mod.info` has `loadModAfter=SWMG,HBVCEFb42,HBTacReload`. Gunworks' `Hooks/StackedMagazineHooks.lua` (2026-11-22) replaces `ISEjectMagazine:unloadAmmo` for a stacked pack in the gun (`StackedMagazines.EjectPack`) without calling the version it found. Loaded before Gunworks, the carry's wrap is that version, so a pack's assignment stayed on the gun. Loaded after, the carry wraps Gunworks' hook and finds the new pack by its ID like any ejected magazine. Hot Brass is listed so the whole gun stack sits under this mod the same way (Tactical Reload itself loads after SWMG, and its framework wraps `ISInsertMagazine:animEvent`); nothing of ours depends on it today, since the `doSpawnCasing` wrap waits for `OnInitGlobalModData` either way.
- Hot Brass Tactical Reload (`HBTacReload`) ejects without `ISEjectMagazine`: it creates the magazine itself and drops it through `SpentCasingPhysics.doSpawnCasing(..., optionalItem, ...)`. That function is wrapped to move the assignment onto `optionalItem`. The wrap is installed on `OnInitGlobalModData`, because `doSpawnCasing` is defined in Hot Brass's server folder. It works because that item object itself is what `AddWorldInventoryItem` later puts on the ground, so its modData lands with it.
- `hasModData()` guards `GetAssignedAmmo`, because the tooltip calls it for every hovered item and `getModData()` would create a table on each one.

### Weapon kinds
`GetFeedKind` classifies the gun in hand in the same order Gunworks' `BeginAutomaticReload` does: a Gunworks magazine profile, then Gunworks speedloaders, then the vanilla `getMagazineType()`.
- `HasMagazineWeapon`: magazine-fed guns (pistols, rifles and anything with a Gunworks magazine profile). Only these have a magazine to eject or insert.
- `HasFeedWeapon`: magazine-fed guns plus Gunworks speedloader guns (revolvers, the Mosin's stripper clip). Speedloaders are stored, refilled and fetched like magazines, but never ejected. See ReloadMagazines for how the revolver itself is loaded.
- `HasSpeedLoaderWeapon`: the speedloader case on its own. The radial entry is labelled "Reload All Speedloaders" for these ("Reload All Magazines" for magazine guns, "Reload All" for other loose-round guns), all under the one `reloadAll` option key.
- `HasAmmoWeapon`: any firearm. Revolvers, shotguns, lever-actions and the hunting rifle load loose rounds straight into the gun. Their rounds are still worth bagging.
- `IsMagazine`: a Gunworks gun can take several magazines (an M4 takes STANAG 20 to 150), but `getMagazineType()` names only the one last inserted. So it checks the profile's set first, or the speedloader list, and then falls back to matching the magazine type against both the short and the full item type, as vanilla B42 does (see `predicateNotFullMagazine`).
- `GetBestMagazine` uses Gunworks' `getBestMagazineForGun` for profile guns. `HandWeapon:getBestMagazine` only knows the one magazine type.

### Stacked (jungle) packs
Gunworks 2026-11-22 added stacked magazines (`WeaponSystems/Utils/StackedMagazines.lua`): Guns of Marz registers `556x45Magazine60_STANAG` + `_2` and `9x19Magazine60_MP5` + `_2` as two 30-round sides. Loose, a pack is one item of the first type, `MaxAmmo` 60, its split in modData `GW_Stacked`. Inserted (`PresentSide` + `SeatPack`), only the side in the well is the gun's count: the gun's `maxAmmo` becomes the side capacity (30), `modData.MagazineType` names the side item in the well, and the other side's rounds live in the gun's modData `GW_Stacked` (`{ group, side, rounds, lists }`).
- `GetGunMagazineFill(weapon)` returns the gun's rounds and capacity counting every side: well + the other sides' `rounds`, against side capacity x sides. Without a split (no Gunworks, an ordinary magazine, a pack inserted before stacked magazines existed) it is `getCurrentAmmoCount()` / `getMaxAmmo()` as before. Used by the eject check in `ReloadMagazines`, `HasReloadableMagazines`, `GetReloadDemands` and `GunRounds`. Before it, a full well (30/30) counted as a full gun, so the reserve side was never topped up, and the eject sync check left the reserve out of the gun's total, so it never matched the ejected 60-round pack and always waited its full second.
- It reads `modData.MagazineType` and `GW_Stacked`, never `getMagazineType()`: on an MP client the gun's magazine type and `maxAmmo` stay what they were until the next equip (`Magazine.RestoreMagazineType`; `SyncHandWeaponFields` carries modData but neither field). Gunworks' own `GetGunState` goes through `getMagazineType()`, so it can't be used on the client.
- **Design: the radial reload ejects the whole pack.** Gunworks' Reload key flips to the other side (`ISStackedMagazine`) whenever that side has rounds, and only swaps magazines when every other side is empty. Reload All instead treats the pack like any magazine: when any side is short, at the end of the run (see End swap) it ejects the pack (`EjectPack` puts it back together as one 60-round item), refills it with the spares and inserts the best magazine. That is the only way to top up the side that is not in the well.
- `GetWeaponRoundTypes`: the gun's whole Gunworks ammo family in the player's reload order, or else its single ammo type. Store and fetch use it, so loose HP or AP rounds are bagged along with ball.

### Menu visibility
- `HasAmmoInInventory` (Store All Ammo) is true only when a full magazine or speedloader would be stored: that is all Store All adds over Store Spent, so otherwise the entry would just repeat the other. `HasSpentAmmoInInventory` is true when Store Spent would move anything.
- `GetFetchableRoundTypes` is empty for magazine weapons. Loose rounds are only worth fetching for a gun that loads them directly (speedloader guns included). A magazine-fed gun wants magazines, and Reload All already draws rounds out of the bags without carrying them first.
- `HasReloadableMagazines` is true for an empty magazine gun with a magazine to hand. It is also true when the magazine in the gun is part-used and there is a spare to swap in, or loose rounds to top it up after ejecting. For any feed weapon, it is true when a non-full magazine or speedloader has rounds to hand.
- `FindReloadableMagazines` returns non-full magazines in priority order: main inventory first, then each worn bag.

### StoreInBag
Queues a move into the first bag that will take the item.
- `isItemAllowed` matters as much as the weight check. A restricted container such as a shoulder holster takes pistol magazines only, yet its weight reduction makes it report room for anything. Without the check it claims items it then refuses. That starves the bag that would have taken them, and it aborts the rest of the queue, because a rejected transfer stops and resets it.
- `hasRoomFor` only sees a bag as it is right now, and nothing has moved while the queue is being built. So each bag is also charged for the weight already promised to it (`reserved`).

### ReloadMagazines
One mode, "Reload All" (2026-11-24; it replaced Reload Magazines and Reload Magazines (Open Boxes)). It always opens boxes for what loose rounds can't cover, and is built for combat readiness: a cancel at any step leaves the gun loaded.
- **The gun's magazine stays in until the end.** Earlier versions ejected a part-used magazine first, so the whole refill ran with an empty gun. Now the spares are refilled first (with every box round they need), and only the last round (no box left to open) ends with the **end swap**: `ISEjectMagazine` + `MagazineBag_ContinueReload`, which plans again once the ejected magazine exists (`ISEjectMagazine` only creates it after its animation). That pass sees an empty gun, inserts the best magazine first, then tops up the ejected one. `run.ejected` allows one end swap per run.
- **Loose-round guns** (`LoadsLooseRounds`: shotguns, lever-actions, revolvers, speedloader guns too). Players found that opening their boxes and bagging the loose rounds by hand beat any reload plan: vanilla's R key (`BeginAutomaticReload` → `ISInventoryPaneContextMenu.transferBullets`) pulls loose rounds out of bags but never opens a box, so boxed rounds cost a box opening mid-fight. So Reload All loads the gun first (pass 1, `BeginAutomaticReload`, opening one box only when nothing can load it), refills speedloaders, then turns boxes into bagged loose rounds, one box per round: bag the loose rounds in the main inventory (`StoreLooseRounds`), open the next box, `ContinueReload`, repeat. `BagBoxDemands` picks the gun's own rounds (`GetFetchableRoundList`: its assignment, else the family in reload order) and opens a box only when its rounds fit in the ammo bags' free room (`getEffectiveCapacity - getCapacityWeight` summed over the bags, minus the loose rounds about to go in, plus the box's own weight when it sits in an ammo bag). A carton or crate counts as one box's worth (`entry.unit`, the innermost recipe's count from `FindSource`); its spare boxes are returned at the end as usual. When the round also queued speedloader loads, it continues first with a loose-round count check (as `StoreRounds`), since bagging rounds the loads are about to take would move items that are gone. `HasLooseRoundWork` shows the radial entry for these guns ("Reload All"). Without Gunworks `RevolverHasRounds` skips the speedloader check.
- **End swap only when it gains something** (`SwapWorthIt`): a spare that will hold more rounds than the gun's magazine (`GetGunMagazineFill`) after this round's refill, loose rounds of the gun's types not already planned (`pools[t].taken`), or a box that could still top the ejected magazine up.
- **An empty gun is loaded first.** When the gun has no magazine, `ChooseInsertMagazine` picks one before anything else is queued: a magazine needing no load goes in at once; one that needs a load is moved to the front of the queue and inserted right after its own load. On equal keys a magazine needing no load wins (fourth key, `ready`), so after the end swap a full spare goes in rather than waiting for the ejected one to be topped up. `run.inserted` stops a second insert in a later round (in MP the gun's `isContainsClip` can lag the insert); the end swap clears it, and so does a walk restart.
- **Planned before queued.** Every magazine's refill is worked out first (`entry.loads`, `entry.bullets`), then the magazine for the gun is chosen, then the actions are queued. The choice needs to know what each magazine will hold after its refill, and the queue needs to know which one stays in hand.
- **Which magazine goes in** (`ChooseInsertMagazine`). The target is the chambered round (the last `AmmoList` entry when a round is chambered), or else the gun's `getAmmoType()`, which Gunworks sets to each round as it's fired, so it's the last round fired. Candidates are every accepted magazine carried, full ones included, judged by their count after the planned refill. A magazine that will hold only the target round wins on round count, then capacity. If none will, the one with the most capacity goes in, then the most rounds. Empty ones never go in. Without Gunworks there is one round type, so this comes down to the fullest magazine, as before.
- **Speedloader guns load first.** Pass 1 hands the revolver to `ISReloadWeaponAction.BeginAutomaticReload`, the R-key reload that Gunworks hooks. An empty cylinder takes the best speedloader, and a part-loaded one takes loose rounds in the player's ammo order. Then `MagazineBag_ContinueReload` refills the speedloaders on pass 2. The order is reversed from magazines because Gunworks' insert hook only empties a speedloader into the cylinder and leaves the item behind. Refilling afterwards tops up the one just used, and planning it on pass 2 sees its real, emptied count.
- `HasReloadableMagazines` for a speedloader gun is also true when the revolver can take rounds: loose rounds on hand, or an empty cylinder with a loaded speedloader.
- **One magazine at a time.** A bag discounts the weight of what it holds, so a whole reload's worth of rounds in hand can push the character over their carry weight. Loading uses up the rounds and each magazine goes straight back into a bag, so only one magazine's worth is carried at any time.
- **One call to getSomeTypeRecurse per round type.** Each type is fetched once, for the combined need of every magazine that accepts it, and the result is handed out in slices. Calling it per magazine would return the same rounds each time, since nothing has moved yet while the queue is built.
- **Switching round type.** Before each load whose type differs from the magazine's current one, `MagazineBag_SetAmmoType` calls Gunworks' `MagazineAmmoProfileSetter`. It runs in the queue, not at planning time, so a cancelled reload never leaves a magazine switched to a round it didn't get. It runs after the magazine has moved to the main inventory, because Gunworks' server handler only looks there.
- **Each load is capped.** Vanilla `ISLoadBulletsInMagazine` ignores its `ammoCount`: it loads until the magazine is full or the main inventory has none of that round left. A mixed plan (10 ball, then 20 HP) would have the ball load swallow every ball round in hand, including rounds moved there for later magazines, and fill up, so the HP load does nothing and the HP rounds are left in hand. So each load passes Gunworks' extra `ammoLimit` and `ammoTypeOverride` arguments (the same ones its own `reloadMagazine` uses). Without Gunworks they're ignored, and with one round type the overdraw only shifts rounds between magazines. On a server the cap needs the `serverStart` hook in `MagazineBag_GunworksHooks.lua`, or a part-used magazine stops short.
- `ISLoadBulletsInMagazine` only draws from the main inventory, so rounds are moved there first. The move uses `MagazineBag_TransferAction` rather than `transferIfNeeded`, which uses the vanilla action: a refusal there would reset the queue and abandon the reload.
- Bag magazines are taken out to load and put back afterwards. A filled magazine is put away before the next one starts, so its weight doesn't follow the character through the rest of the sequence. The one headed for the gun stays in hand.
- `ISInsertMagazine` needs the magazine in the main inventory, not in a bag.
- **Bagging the leftovers.** The plan only moves and loads the rounds it counted, so loose rounds stay in the main inventory: ones the player already held there that no magazine needed, rounds moved out for a load `AwaitRounds` skipped, or a load that came up short. So the run's last step (the main path's end, after the gun load and `ReturnLeftovers`, never on a pass that continues) is `MagazineBag_StoreRounds`, which bags every loose round in the main inventory whose type the gun or any carried magazine or speedloader takes (`GetRelatedRoundTypes`: each one's Gunworks family, else its `getAmmoType()`; magazines of each type looked at once). Favourited rounds stay. The same step then bags every box, carton or crate of those rounds left in the main inventory (`MagazineBag_Boxes.GetSourceTypes`, the opener map walked up to `MAX_DEPTH`), the ones the run never touched included; rounds go first so they get the bag room. See MagazineBag_StoreRounds.lua.

### FindBagForItem
The first worn bag that will take the item right now, skipping the one that just turned it away. It's used when a queued move reaches a bag that has filled up since the move was planned.

### StoreAmmoToBag
`CollectStorable` decides what goes (2026-11-24), from the main inventory only:
- **Every carried gun counts** (`CarriedGuns`): both hands, every gun attached to the hotbar (`getAttachedItems`), and every gun on Tien's Customizable Hotbar (its global `TienCustomizableHotbar.Slots(player)` + `Steps(slot)`, slots and steps alike; called under `pcall`, skipped when the mod isn't loaded). Such an entry is `{ id, type }`: the exact item by `getItemWithIDRecursiv`, else any carried item of that full type (`getFirstTypeRecurse`), so a slot whose gun was swapped for another of the same model still counts; a gun not carried at all adds nothing. Its own `Resolve` is not used: it walks the whole tree with match scoring for each slot, too much for every radial open. Each gun's magazines or speedloaders (`IsMagazineForGun`, the old `IsMagazine` taking a gun instead of the one in hand) and its round types (`AddRoundTypes`: Gunworks family, else `getAmmoType()`).
- **Magazines:** empty and part-used ones, full ones too for Store All. A magazine attached to the hotbar or held stays: bagging it would drop it from its slot.
- **Loose rounds, then boxes, cartons and crates** of those rounds (`MagazineBag_Boxes.GetSourceTypes`), through `StoreLooseRounds` with the magazines' `reserved` weights; favourites stay.
Loose rounds are queued after the magazines, one run per round type. The transfer action only bulk-merges back-to-back moves of the same item type into the same container.

### FetchFreshAmmoFromBag
Fetches only what the character can carry without becoming encumbered.
- `hasRoomFor` on the main inventory checks the hard capacity. That is well above where Heavy Load sets in, which is the inventory's `getMaxWeight()` (the same limit `ISHotbar` checks). So the budget is `getMaxWeight() - getCapacityWeight()`, which is skipped when the character has unlimited carry.
- An item in a worn bag already counts toward the character's weight, discounted by the bag's weight reduction. Taking it out only adds back the part the bag was hiding: `weight * getWeightReduction() / 100`. A running total covers the moves the queue hasn't run yet.
- `hasRoomFor` stays in as the hard cap, with its own running total.
- Two passes over the bags: full magazines and speedloaders first, then loose rounds. Both share one weight budget, so without the ordering, loose rounds a revolver owner also wants could use up the budget and leave the speedloaders in the bag.

### Opening ammo boxes
Only Reload All opens boxes. Fetch Fresh Ammo (Open Boxes) was dropped on 2026-11-24: Reload All opens boxes into the bags, and the Reload key takes loose rounds and magazines out of the bags itself (`transferBullets`, Gunworks' `getBestMagazineForGun` both search recursively).
- `GetReloadDemands` lists what the reload will need: each reloadable magazine or speedloader, plus the gun itself when it's a part-used magazine gun (its magazine becomes a spare after the eject) or a speedloader revolver. Each entry uses the same `GetReloadRoundTypes` the reload uses, so assignments decide which boxes are worth opening.
- **One box at a time.** Opening every needed box up front would put all their rounds in hand at once. That breaks the one-magazine's-worth rule and can leave the character encumbered. So Reload All runs in rounds, each ending in one `MagazineBag_ContinueReload`:
  1. Each round refills magazines from the loose rounds on hand, and each one goes back to its bag.
  2. It collects what's still short (`shortfall`) and opens **one** box for it (`MagazineBag_Boxes.OpenOne`).
  3. It plans again once that box's rounds exist. Opened rounds don't exist until the craft finishes, the same reason the eject needs a second pass.
  4. Every refilled magazine goes back to its bag, except one going into an empty gun. The end swap waits for the last round, when no box is left to open.
- **Loose rounds count as used.** A magazine still short after the refill plan has used up every loose round on its list. So the shortfall is planned with `looseUsed` (loose rounds count as 0), not counted again.
- **`run`** (`boxRun` in ContinueReload) comes from `MagazineBag_Boxes.NewRun()`, made by `ReloadMagazines` when the radial calls it with none, and also carries `ejected` / `inserted`: `tried` holds the IDs of every box, carton or crate already opened, and `leftovers` what a carton or crate released (see the Boxes section below). It's carried through `ContinueReload`, including across the eject pass. A box that fails to open (its recipe refused) is skipped from then on, so the loop always ends.
- **Cartons and crates** take a round each, like a box. Opening one gives boxes (or cartons), not rounds, so the next round finds those and opens one of them. Its `synced` check waits for the container to be gone and the count of what it holds to have grown (`MagazineBag_Boxes.SyncedAfterOpen`). The loads queued in the same round don't touch boxes, so they can't upset that count.
- **The last round** (no more containers to open, or the next one would not open) ends with the end swap if one is due, else `ReturnLeftovers` and `StoreRounds`.
- **Speedloader revolvers:** pass 1 opens one box first, but only if the revolver has nothing to load from (`RevolverHasRounds`: no loose rounds, and for an empty cylinder no loaded speedloader).

## MagazineBag_Boxes.lua
- **Finding boxes.** Built once from the game's craft recipes, so vanilla, Gunworks packs and any other mod's boxes are found without a list. A candidate is a recipe with one item input (amount 1) and one item output (amount > 1). The box has to name that recipe as its `DoubleClickRecipe`. That rule leaves out conversion recipes such as Guns of Marz's `Convert_MarzGuns_to_SWMG`, which also turn one item into rounds. Mapped outputs are resolved with `OutputMapper:getPatternForResult(round)`, which returns the box `Item` scripts for that round. Unmapped ones use the input's possible items.
- **Cartons and crates.** The same rule finds them: vanilla's `OpenCarton12`, Guns of Marz's and Guns of Tien's `OpenCartonOfBoxesOfAmmo` / `OpenCrateOfBoxesOfAmmo` are one in, 12 or 4 out, named by the item's `DoubleClickRecipe`. So the map (`openersByItem`) is keyed by whatever comes out: a round lists its boxes, a box type its cartons, a carton type its crates. `FindSource` looks for a box of any listed type first, then a carton for any of those box types, then a crate (`MAX_DEPTH` 3, which also stops a mod's recipes that open into each other). It returns the container, the recipe, what it opens into (`outputType`, `outputCount`) and the rounds it ends up as (`yield`, the counts multiplied: a crate of 50-round boxes is 4 × 12 × 50). `IsContainerOfBoxes(entry)` is true when `outputType` isn't the round.
- **`Plan`.** Loose rounds are used first, and a box is opened only for what they can't cover. A box's rounds count as available for later demands, so one box can serve several magazines. A carton or crate counts as its whole `yield`. Options: `looseUsed` counts loose rounds as 0. `skip` is a set of box IDs to leave alone.
- **Leftovers.** A vanilla shell carton weighs 15 and a GoM 9mm crate 12.4. Opening one puts every box (or carton) it held in the main inventory. Only a few are needed, so the rest go back to the bag the container came from when the run ends. Before each carton or crate opens, `RememberLeftovers` notes its bag and the IDs of that output type already in the main inventory (`before`), so items the player already kept there are left alone. A carton that itself came out of a crate has no bag of its own (it's in the main inventory), so it takes the crate's bag from the record whose output it is. `ReturnLeftovers` queues a `MagazineBag_TransferAction` for each new item of each recorded type in the main inventory (each item once), so a full bag sends the rest to another bag, or they stay.
- **`SyncedAfterOpen`** (a carton or crate opened by Reload All, MP): each container gone, and each output type grown by what it holds. A box being opened is itself one of the boxes counted, so the expected count leaves the opened containers out.
- **Opening.** Goes through vanilla `ISInventoryPaneContextMenu.OnNewCraft`, the same path as opening a box from its right-click menu. It checks the recipe and moves the box into the main inventory, where the rounds come out. That move uses the vanilla transfer action. A refusal would reset the queue, but moving a worn bag's item into the main inventory is practically never refused.

## MagazineBag_TransferAction.lua
A plain vanilla transfer with one change: where the item ends up.
- **Presentation is left alone.** An earlier version forced `CharacterActionAnims.RemoveBullets` on top of the transfer animation. That clip loops and is driven by anim events: its only vanilla user, `ISUnloadBulletsFromMagazine`, returns `getDuration() == -1` and ends the loop from an animEvent. A timed transfer handles no such events, so the character got stuck at the loop's hold point.
- **`resolveDestination`.** A restricted bag only turns an item away when the move actually runs. A shoulder holster reports room right up until it holds its second magazine, so a queue planned while it was empty sends too many items to it. Those items are redirected to the next bag that will take them. If none will, the move is dropped quietly, because a transfer that fails outright resets the whole queue behind it. This runs before `ISInventoryTransferAction:start` creates the item transaction, so the move is registered against the bag the item actually goes into.
- **`isValid` never returns false.** A failing action calls `stop()`, which resets the whole timed action queue, so one refused move would cancel every later step of the reload. Setting `dontAdd` uses vanilla's own no-op path: `start()` zeroes the timer and `transferItem()` moves nothing, so the action completes having done nothing and the queue carries on.

## MagazineBag_ContinueReload.lua
`ISEjectMagazine` creates the ejected magazine with `instanceItem()` when its animation finishes. That means the item doesn't exist while the reload is being planned. This action sits after the eject and runs the planning again, when the magazine is an ordinary spare.
- **Waiting for the server (MP).** On a client the eject, the speedloader insert, the loose-round revolver reload and the box craft all run on the server (`loadAmmo`/`unloadAmmo`/`animEvent` skip their work when `isClient()`). The client only learns the result from `SyncItemFields`/`SyncHandWeaponFields`/add and remove item packets, which are RELIABLE but unordered, while the action's Done is RELIABLE_ORDERED, so the Done can arrive first. The next action starts the moment the Done is handled, so planning straight away sometimes saw the state from before: the speedloader just emptied into the revolver still looking full, or rounds the revolver had just taken still in the inventory. The plan then either found nothing to do, or queued a load whose rounds were gone; that load's `start()` calls `forceStop()`, which resets the queue. Either way the reload stopped after the first step, and a second use of the radial worked.
- So in MP each `ContinueReload` carries a `synced` check and holds in `waitToStart` until it passes, at most `SYNC_WAIT_MS` (1 s). A timed-out wait just plans with what it sees, as before, and prints the check's numbers to the console (`[TienMagazineBag] MagazineBag_ContinueReload went on after ...`): each check returns a second value describing what it compared. The limit was 3 s, and a check that never passed (seen after box openings) left the character idle long enough to look like the reload had stopped. A working check passes within one round trip, so 1 s is plenty. The checks count every round the character carries: the gun (plus a chambered round), loose rounds of the gun's family, and every magazine or speedloader in any carried container. An eject and a gun load only move rounds, so they wait for that total to match the snapshot taken when they were queued: after an eject the gun must also show no magazine, and after a gun load the gun's own count must have changed. A box open waits for the box to be gone and the total to have grown by the box's output (`count` from the recipe). The loads queued before a box opening in the same round only move rounds, so they don't upset the total.
- A check is only made when the step actually queued something (`QueueSize` before and after), because otherwise nothing will ever arrive and the wait would just cost the full limit. Single player needs none: the actions change the state directly.
- **Restarting after a walk.** Every reload step (eject, insert, load, rack, transfers within the character's inventory) can be done while walking; only running stops them. The one step walking can stop is opening a box, carton or crate whose recipe lacks the `CanBeDoneWhileWalking` tag (vanilla's `OpenCarton12`; GoM's recipes before Guns of Tien tags them). Java then clears the whole queue (`StopAllActionQueueWalking`), and the Lua queue's `resetQueue` calls `forceCancel()` on each action that hasn't started. Such an opening is always followed by a `ContinueReload`, so its `forceCancel` sees the cancel. If the character is walking (`isPlayerMoving()` or `pressedMovement(false)`) and not running or sprinting (running counts too for a Running Reload master, below), it notes a restart for that player. `OnPlayerUpdate` runs it once the player stands still and isn't aiming. Restarting at once would reach the same opening and be cancelled again. The restart runs the plan again from scratch (`ReloadMagazines` pass 1) with the same `boxRun`, so the leftover records still send the boxes back to their bag. It clears `tried`, because the container whose opening was cut short is still there. It's dropped if the player starts running or sprinting (not for a master), or another timed action begins, so running is the way to really cancel. A cancel while standing (Esc, a refused step) restarts nothing.
- **Tien's Skill Mastery, Running Reload** (signature `Firearms.SigRunReload`). Its `ISBaseTimedAction:create` wrapper sets `stopOnRun = false` on the vanilla reload actions only (`ISReloadWeaponAction`, `ISInsertMagazine`, `ISEjectMagazine`, `ISLoadBulletsInMagazine`, `ISRackFirearm`, the two unloads), by `Type`. Java stops the whole queue when the action at its front has `stopOnRun`, so a master who ran during this mod's reload lost it at the first step of ours: a transfer, `AwaitRounds`, `SetAmmoType` or `ContinueReload`. `MagazineBag_Core.HasRunningReload(player)` asks `TienSkillMastery.sig` (false without that mod, or if the call errors: `pcall`). Those steps take `stopOnRun` from it: `AwaitRounds`, `SetAmmoType`, `StoreRounds` and `ContinueReload` in `new`, the transfer in `create` (it has no `new` of its own, and `create` is where Java reads the flag). They apply to Fetch and Store too, as they are the same actions. Box openings (vanilla `ISHandcraftAction`) still stop on running; for a master that counts as a walk-cancel, so the run restarts once they stand still.

## MagazineBag_BoxAnimSync.lua
Sandbox option `TienMagazineBag.BoxAnimationSync` (on by default; `media/sandbox-options.txt`, text in `Translate/EN/Sandbox.json`). Reported 2026-11-13 on 42.22: watchers saw a player opening an ammo box during Reload All stand still with the box in hand (the box prop shows, so the start reached them) until that player moved or cancelled. Not reproduced or logged yet, so every likely cause is covered.
- **How another player's action reaches you (42.22, traced).** `BaseAction.setActionAnim` enters `PlayerActionsState` as a sub-state and sends a `StatePacket` whose params are the anim variables of `getCharacterActions().get(0)` read at that moment (so a variable set after `setActionAnim` is missed: `ISHandcraftAction:start` sets the script's `AnimVarKey` after it). On the watcher, the enter is queued and applied only once its copy is within 0.2 tiles of where the action began: it builds a new `BaseAction` from those variables, sets `IsPerformingAnAction`, the hand-model override (the box prop) and calls `setAction`, which replaces the previous action without stopping it. An exit is applied at once (its `stopAction` clears that action's variables) unless the copy isn't in the state yet and an enter is still queued, in which case it only cancels that enter. The sender also cancels a not-yet-sent enter when an exit of the same state follows in the same frame (`NetworkState.tryCancelPendingEnterPair`), and every timed action shares that one state. So when a step's exit is lost, its variables stay on the watcher's copy.
- **Why the box loses.** Vanilla's `OpenAmmoBox` node (the `timedAction` of vanilla and Gunworks boxes, `time = 15`, ~0.3 s on a server) has a single condition, `PerformingAction`, and is not looped. Reload nodes match on more, and Hot Brass alone has 168 action nodes that match only on `isRacking`, `isUnloading` or `RackAiming`. A leftover `isLoading` / `isRacking` / ... from the previous load or rack therefore outranks it. Gunworks' remote sync only clears its own `GunworksReloadAnim`. The copy can also miss the `actions` state: aim / idle → actions needs `IsPerformingAnAction` true and `isTurning` false, and `IsPerformingAnAction` also arrives with every player packet.
- **Leftover strings.** `GunworksReloadAnim` and `GunworksStackedReload`. Gunworks' stacked-pack flip (`ISStackedMagazine`, 2026-11-22) sets `GunworksStackedReload` and never clears it, and `ReloadAnim/Sync.lua` prefers a non-empty one over the gun's own reload type on every later reload, so it is cleared with the rest. `Sync.lua` now clears a leftover `GunworksReloadAnim` itself whenever `PerformingAction` isn't "Reload", so clearing that one here is redundant; it is kept because it costs nothing and the sender's "" rides the enter, so it is gone on the watcher before Gunworks' next 3-tick pass.
- **Sender.** `ISHandcraftAction:start` is wrapped: for an `OpenAmmoBox` craft on an MP client it sets the reload flags to false (and the leftover strings to "") as anim variables before vanilla's `start` calls `setActionAnim`, so they ride the enter and reset every watcher's copy. The craft's own end clears them again locally, where they are already off. Applies to boxes opened by hand too.
- **Watcher.** Every 3 ticks, for each remote player showing `OpenAmmoBox`: clear any leftover flag, set `isTurning` false, and set `IsPerformingAnAction` true while the copy isn't moving. After 3 s (no box opening is that long) it ends the animation on the copy (`PerformingAction` cleared, `IsPerformingAnAction` false). The box prop itself can't be cleared from Lua (`NetworkCharacterAI` and the override fields aren't exposed); the next action replaces it.

## MagazineBag_StoreRounds.lua
Queued at the end of a reload run (see ReloadMagazines). It plans when it runs, not when it is queued, because only then do the loads' results exist.
- **Waiting for the server (MP).** The loads run on the server, and their round removals reach the client unordered with the Done (see ContinueReload). Planning early would queue moves of rounds the server has already loaded, and a failed move resets the queue. So `QueueStoreRounds` works out how many related loose rounds the main inventory should hold at the end: what it holds now, plus the rounds the plan moves in from bags, minus the rounds it loads. The step holds in `waitToStart` until the count matches, at most 1 s (a timeout prints the numbers and goes on). A skipped load leaves the count off, so that case costs the full second. Single player doesn't wait.
- One run per round type, like StoreAmmoToBag, so the transfer action can merge them. `StoreInBag` sees each bag as it is by then, the refilled magazines already back in it.

## MagazineBag_AwaitRounds.lua
Queued before each load (and before its `MagazineBag_SetAmmoType`). `ISLoadBulletsInMagazine:start` (and Gunworks' override of it) calls `forceStop()` when the main inventory has none of the round, and a stop resets the whole queue: the character pulled a blank speedloader out of its bag and then did nothing more. In MP the rounds can be missing for a moment even when the plan was right (they arrive in their own packets), or for good when the plan was built from a client that hadn't caught up. So it waits in `waitToStart` until the round is in the main inventory, at most 1 s (MP only; a timeout is printed to the console; in single player the state is already final). If the round still isn't there, it takes its load and ammo type switch out of the queue (`dependents`) and lets the rest of the reload carry on, so the magazine is put back unfilled instead of the reload ending.

## MagazineBag_SetAmmoType.lua
It sets the type before `ISBaseTimedAction.perform`, because that call can start the next action right away. The next action is the load, and `ISLoadBulletsInMagazine:start` checks the magazine's ammo type.

## MagazineBag_GunworksHooks.lua
Makes Gunworks' own reloads (the R key, its radial and "reload all magazines" paths) follow assignments. Gunworks calls these through the module table on every use, so replacing the table field is enough.
- `Ammo.GetAutomaticReloadAmmoType` returns the item's assignment. It returns it even when none of that round is carried: Gunworks then loads nothing, where a nil would let it fall back to the gun's current type. Magazine-fed guns are skipped, because their key belongs to the inserted magazine, and Gunworks never asks for their round type anyway.
- `SpeedLoader.GetBestSpeedLoaderForGun`: for an assigned gun, only a speedloader holding nothing but the assigned round (checked through its `AmmoList`, or its ammo type when there is none). If there isn't one, Gunworks falls through to loading loose assigned rounds.
- **Capped loads on a server.** `ISLoadBulletsInMagazine:serverStart` records `ammoCountStart` from the server's own magazine when it's missing. Gunworks' `isLoadFinished` ends a capped load once `getCurrentAmmoCount() - ammoCountStart` reaches `ammoLimit`, and only `start()` sets `ammoCountStart`. In MP the server never runs `start()`: `NetTimedAction` rebuilds the action with `new()` from the client's fields named like its parameters, then calls `serverStart`. So the server counted the whole magazine as loaded this session, and a capped load stopped once the magazine held `ammoLimit` rounds. A 150-round drum at 75 asked for the missing 75 loaded nothing, one at 30 stopped at 120, and the rounds moved out for it were left loose in the main inventory. Gunworks' gun reload isn't affected, because it sets `ammoCountStart` in `new()`. Vanilla reads `ammoCountStart` only in `update()`, which the server doesn't run.

## MagazineBag_AmmoMenu.lua
"Assign Ammo ▸" and "Unassign Ammo" apply to every selected magazine, speedloader or loose-round gun of the first one's family. Only carried items are offered, because the server applies the assignment by searching the player's inventory. The round counts shown are what the player carries, bags included.

## MagazineBag_Tooltip.lua
Other mods replace `ISToolTipInv:render` wholesale. Guns of Marz does it when its file loads. ZomboidFixesB42 does it on `OnGameStart`, and draws every `WeaponPart` itself without calling the previous render; Guns of Marz magazines are weapon parts. So the wrap is installed on the first `OnTick` after `OnGameStart`, after every `OnGameStart` handler has run, and so on top of whichever render ends up in place. Installed on `OnGameStart` itself, it was sometimes under ZomboidFixes: guns showed the row and magazines didn't. 
- **The row is part of the tooltip, not drawn after it.** Drawing it below a finished tooltip gave it its own background and border, with a divider line and columns that didn't line up. Instead, for the length of one render call, the item class's `DoTooltip` and `DoTooltipEmbedded` are wrapped on its metatable (the same technique as StarlitLibrary), then always restored, under `pcall`.
- **Renderers that build the layout themselves** call `DoTooltipEmbedded(tooltip, layout, offsetY)` from Lua (ZomboidFixesB42, StarlitLibrary). The row is added straight into their layout, so it lines up with the stat rows.
- **The vanilla path, and Guns of Marz,** call `DoTooltip(tooltip)`. Java then calls `DoTooltipEmbedded` itself, where Lua can't see it, so the row goes in its own small layout directly after the item's own content, inside the same `DoTooltip` call. The render's measuring pass includes it, so the one background and border cover it. A layout sizes its columns by itself, so a separate label/value row would leave a wide gap before the value. In this case the row is written as one label, "Assigned Ammo: <round>". `addedToLayout` stops the row being added twice when a `DoTooltip` replacement (Starlit's) routes through `DoTooltipEmbedded`.
- **Padding** can't be read, because instance fields are hidden from Lua. It's recomputed the way the game sets it, from the width of one digit (as ZomboidFixesB42 does).

## MagazineBag_Options.lua
- Option keys are deliberately not derived from the entry labels. Renaming an entry must not silently reset what players have already turned off.
- Anything that can't be read counts as enabled, so a setting the game hasn't registered or loaded is never why an entry goes missing. Reload All has its own key (`reloadAll`, on). The dropped options (`reloadMagazines`, `reloadMagazinesOpenBoxes`, `fetchFreshAmmoOpenBoxes`) are ignored if saved.
- B42 ships `PZAPI.ModOptions`. The main options screen only builds its mod panel if something has registered by the time that screen is created, which is before `OnGameStart`. So registration runs as the file loads.

## MagazineBag_RadialMenu.lua
In B42, `fillMenu` is an instance method. Its data is the menu object, with `character`/`playerNum` set in `ISFirearmRadialMenu:new`.
- `ENTRIES` is the one list of what the mod offers (option key, key bind, icon, label, `available`, `run`); the radial and the hotkeys both walk it, so a key does exactly what its slice does and only when the slice would show (ammo bags worn too).
- **Hotkeys** (2026-11-24, user's request: one per entry, unbound by default): vanilla key bindings, the pattern ZomboidFixesB42's CLAUDE.md describes (mod options would drop Shift/Ctrl/Alt): section `[Ammo Bags]` and binds `TAB Store Spent`, `TAB Store All`, `TAB Reload All`, `TAB Fetch Fresh` (`key = 0`) appended to the global `keyBinding` once at file load, labels `UI_optionscreen_binding_<name>` in `Translate/EN/UI.json`, tested with `getCore():isKey` in `OnKeyPressed` (fires on release, like vanilla's hotbar keys), player 0 only, not while paused or dead. Store keys work without a gun in hand (the hotbar guns still count); the others need one, as their checks do.

## MagazineBag_Server.lua
In B42 MP the server's copy of the inventory is what gets saved. Bag and ammo assignments made client-side have to be applied here too, or they vanish on logout. The item is found with `getItemWithIDRecursiv`, so a magazine in a worn bag is found as well. An earlier hand-written search called `getItemContainer()` on every item it passed, but only container items have that method in B42. Any other item threw an error, so assignments to magazines in bags never reached the server. They then disappeared on relog, and after any server update to the item.
